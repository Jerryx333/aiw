## 二、今天那单为什么被丢（已复现）

`state/runs/20261107-071342-codex-sol-98085-765baef3/output.md` 末尾块里只写了一个「无」。
派单提示原文写的是「如实写，无则写无」（`findings.py:31`），解析器却要求至少一个已知字段（`findings.py:212`），
于是报「记录块没有已知协议字段」并整块忽略。是**提示和解析器自相矛盾**，不是座位乱写。
把同一块改成 `guess: 无` 就能解析通过（已跑过）。

另：CLAUDE.md 要求执行方最后一行写「结果：成功 / 结果：失败：原因」，但 aiw 代码里**没有**解析这一行，全靠主会话肉眼看。

## 三、差距与做法

### 第 1 条 结构化结果
- 新开关 `--schema <JSON Schema 文件>`（单派、会诊、流水线都能用）。aiw 在说明末尾追加格式要求：最后用 `<<<AIW-RESULT … AIW-RESULT>>>` 包一段 JSON。
- 校验用标准库实现常用子集（type / properties / required / items / enum / minItems / additionalProperties），不引第三方库。
- 不合格：同一座位自动重交一次，说明里附上次原文和具体错误；还不合格 → 非零返回码 + 明确错误，原文完整保留在 output.md，不剥离。
- 合格：run 目录写 `result.json`，stdout 最后一段就是这份 JSON，程序可直接读。
- 顺带修：观察记录块只写「无」视为合法空块；「结果：成功/失败」行解析进账本（缺了标「未声明」）。

### 第 2 条 多步串联 `aiw flow <流程文件>`
- 流程文件（JSON）列步骤，三种：`fanout`（几家并行，同一说明）、`each`（对上一步结构化结果里的每一条各派一单）、`reduce`（全部到齐后汇总，可由座位写或纯程序合并）。
- 流式推进：上游任一份结果一回来就展开派下游，不等全部；每一单的开始/结束写进 `events.jsonl`，可据此证明「A 家的核实在 B 家评审交回前已开始」。
- 复用 panel/map 的派单子进程与中断处理；执行方里禁止再起流水线（沿用 AIW_NESTED）。

### 第 3 条 断点续跑
- 每一单的钥匙 = 座位 + 最终说明全文 + 上游输入 + schema 的哈希（同 goal.py 的做法）。
- `aiw flow <流程文件> --resume <流水目录>`：钥匙相同且已成功、结果合格的单直接复用；说明改了的那单及其下游重派；中断时正在跑的单不算完成。

## 四、拟定验收标准（请老板确认）

1. **格式不对不再悄悄丢**：用假座位测三种情况——第一次错第二次对（自动重交后成功）、两次都错（非零返回码 + 写明哪里不合格，原文保留）、正常（`result.json` 可被程序直接读出）。今天那种只写「无」的观察记录块能正常解析。
2. **一条命令跑通「两家评审 → 每条问题核实 → 汇总」**：假座位让一家快一家慢，事件记录里快的那家的核实单开始时间早于慢的那家交回时间；一家评审失败时其余照走，汇总里标缺席。
3. **断点续跑不重派**：上面的流水线在核实阶段手动打断，再续跑；账本里已完成的单派单次数不增加，只补没完成的；用假座位时最终汇总与不打断跑一遍逐字一致。改了某一步说明后续跑，只有那一步和它的下游重派。
4. **不伤老功能**：现有全部测试通过；不带新开关时单派、会诊、批处理行为不变；跨机转发座位同样做格式校验。
5. **评审与上线**：三条分三次提交在分支上，每条派不同厂商座位评审，评审意见逐条自己复现后再改；合入主干、推送前交老板确认。
